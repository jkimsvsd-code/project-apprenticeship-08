# 설계와 경계

상태: React·Express·SimpleWebAuthn, 로컬 SQLite / 운영 Neon PostgreSQL로 구현하고 실제 HTTPS에서 자동 검증했습니다. 물리 기기는 별도 확인이 필요합니다. API는 src/server/app.ts, 검증은 src/server/auth/webauthn.ts, 저장은 src/server/storage/store.ts 및 postgres.ts에 있습니다.

## 역할

- `src/client/public-profile/`: 과제1의 공개 소개 페이지와 잠긴 공간의 진입점.
- `src/client/private-space/`: 로그인 후에만 받은 본인 비공개 자료의 표시.
- `src/client/passkeys/`: 등록·로그인·로그아웃, 패스키 목록·추가·삭제 화면.
- `src/client/shared/`: 환경 안내, 진행·오류 상태, 목적지 복귀, 접근성 등 공통 UI.
- `src/server/auth/`: 최초 등록 제한, WebAuthn 검증, 질문 수명, 서버 세션.
- `src/server/authorization/`: 세션 사용자 확인과 자료·패스키 소유권 검사.
- `src/server/private-data/`: 본인 비공개 자료 조회.
- `src/server/storage/`: 계정·공개키·질문·세션·자료의 저장소 접근.
- `src/server/config/`: 서버 전용 환경변수 검증, 허용 Origin·RP ID.
- `src/shared/`: 클라이언트에 공개해도 되는 요청·응답 계약과 오류 코드.
- `public/`: 인증 없이 공개 가능한 이미지 등 정적 자산만 보관.

## 주요 흐름

| 흐름 | 처리 순서 |
| --- | --- |
| 최초 등록 | 공개 방문과 분리된 서버 관리 초기 설정 → 소유자 확인 → 등록 질문 → 응답 검증 → 계정·공개키 확정 → 초기 설정 닫기 |
| 추가 등록 | 기존 세션 확인 → 본인 계정의 등록 질문 → 응답 검증 → 별도 credential 저장 |
| 로그인 | 질문 발급 → 기기 서명 → 서버 검증 → 서버 세션 발급 → 검증된 내부 목적지 복귀 |
| 로그아웃 | 서버 세션 폐기 → 쿠키 제거 → 비공개 클라이언트 상태 비우기 |
| 비공개 조회 | 세션 확인 → 세션의 사용자로 소유권 검사 → 본인 자료 조회·반환 |
| 패스키 삭제 | 세션·소유권 확인 → 마지막 패스키 여부 확인 → 선택한 credential 폐기 → 목록 갱신 |

최초 등록은 npm run bootstrap 관리 CLI가 생성한 15분·일회 교환 링크로 제한합니다. 교환 후 임시 등록 준비 쿠키를 발급하며 등록 완료 전에는 users·credentials를 확정하지 않습니다. 공개된 계정 ID나 먼저 접속한 사람을 소유자 증명으로 사용하지 않습니다.
다른 기기에서 추가 등록할 때도 기존 패스키로 인증한 본인만 추가할 수 있어야 합니다.

## 인증 정책

- 패스키 검증에는 검증된 WebAuthn 구현을 사용하고 실제 선택 이유를 설명서에 기록합니다.
- 서버는 credential ID, 공개키, 소유자, 이름, 등록일 등 필요한 메타데이터를 보관합니다. 개인키·생체정보는 받지 않습니다.
- 등록·로그인 질문은 암호학적 난수로 생성하고, 용도·진행 중인 요청에 묶어 서버에서 관리합니다.
- 질문의 만료와 원자적인 일회성 소비를 처리합니다. 취소한 등록은 확정하지 않고 임시 질문은 폐기·만료 처리합니다.
- 서버는 질문·Origin·RP ID·서명·사용자 확인 등 선택한 라이브러리의 필수 검증을 수행합니다.
- 서버 저장형 세션을 사용하고 운영 쿠키에는 HttpOnly·Secure·적절한 SameSite 정책을 적용합니다.
- 상태 변경 요청에는 출처·CSRF 검사를 적용합니다. 로그아웃은 서버 세션을 무효화해야 합니다.

## 자료 격리와 노출 방지

- 로그인 여부와 자료 소유권을 서버에서 모두 확인합니다. 미인증은 401, 타인 자료 직접 접근은 403을 검증 목표로 삼습니다.
- 본인 목록 API는 클라이언트가 보낸 계정값을 권한 근거로 사용하지 않고 세션 사용자로 조회합니다.
- 타인의 자료 ID를 직접 지정한 요청은 거절합니다. 본인 목록의 계정값 변조와 별개의 검증으로 남깁니다.
- 인증 응답·비공개 자료는 공유 캐시에 저장하지 않습니다. 미인증 HTML·직렬화 데이터·공개 번들에 비공개 내용을 넣지 않습니다.
- 로그아웃·세션 만료 시 비공개 UI 상태와 자료 캐시를 비웁니다.

## 분실·삭제 정책

- 한 계정에 별도의 credential ID를 가진 패스키 2개를 등록해 검증합니다.
- 목록에는 이름과 등록일을 표시합니다. 같은 패스키의 기기 간 동기화를 별도 2개로 세지 않습니다.
- 마지막 패스키의 삭제는 서버에서도 차단하고 추가 등록을 안내합니다.
- 초기 미등록 상태는 일반 로그인을 허용하지 않습니다. 모든 패스키에 접근할 수 없으면 자동 복구를 제공하지 않습니다.
- 기기 분실·저장 제공자 접근 상실까지 해결하는 복구 절차는 이번 범위 밖입니다.
- 서비스의 등록 삭제와 기기·패스키 제공자 저장 항목 삭제는 별개임을 안내합니다.
- 저장 제공자는 브라우저 정보만으로 단정하지 않고 실제 등록 과정에서 확인한 내용을 설명서에 기록합니다.

## 검증 계정과 데이터

E2E 계정 A·B는 가상 검증용이며 첫 등록 시 각각 다른 자료 3개를 생성합니다. 계정 A에는 패스키 2개, B에는 최소 1개를 별도로 등록합니다.
fixture의 계정 ID는 인증 수단이 아닙니다. 계정 전환 우회 버튼이나 공용 소유자 패스키는 만들지 않습니다.
실제 credential·세션·운영 자료는 fixture에 저장하지 않습니다.

참고: [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/), [FIDO 패스키 안내](https://fidoalliance.org/passkeys/).
동기화형 패스키가 있으므로 개인키가 항상 단일 기기에만 존재한다고 설명하지 않습니다. 이 서비스 서버가 개인키를 받지 않는다는 점을 검증합니다.

## 실제 API와 운영 경계

| API | 동작 |
| --- | --- |
| POST /api/setup/exchange, GET /api/setup | 초기 링크를 HttpOnly 등록 준비 쿠키로 교환·확인 |
| POST /api/auth/registration/options, /verify | 최초 또는 본인 추가 등록 |
| POST /api/auth/authentication/options, /verify | discoverable 패스키 로그인 |
| POST /api/auth/cancel, /logout | 질문 취소 또는 서버 세션 폐기 |
| GET /api/session | 공개 가능한 세션 요약만 반환 |
| GET /api/passkeys, DELETE /api/passkeys/:id | 본인 키 목록·삭제, 마지막 삭제는 409 |
| GET /api/private/items, /api/private/items/:id | 세션 본인 목록, 타인 자료 직접 요청은 403 |

모든 상태 변경 요청은 Origin·JSON 형식을 검사합니다. 운영 쿠키는 __Host- 접두사·Secure·HttpOnly·SameSite=Strict입니다.
질문 300초, 세션 3600초가 기본이며 서버에 해시한 세션·초기 링크·등록 준비 값만 저장합니다.
질문은 브라우저 흐름·용도·계정·등록 주체에 묶이고 DELETE RETURNING으로 소비합니다.
서명 검증의 비동기 처리 뒤에도 저장 트랜잭션에서 세션·credential을 재확인합니다.
삭제한 패스키로 생성한 모든 세션은 외래키 연쇄 삭제로 무효화합니다.
브라우저는 세션 만료·로그아웃·탭 전환·뒤로 가기 복원 시 개인 공간을 다시 확인하고, 사용자별 컴포넌트 키로 자료 혼합을 막습니다.
개발용 Vite에도 runtime·server·tests·evidence·docs의 직접 파일 요청 차단을 적용합니다.

운영 진입점 server.mjs는 빌드한 src/server/vercel.ts를 불러옵니다. pg Pool은 Vercel attachDatabasePool과 연결하고 TLS 인증서를 확인합니다. 사용자별 트랜잭션 잠금으로 로그인 완료·키 삭제의 경합을 처리합니다. [운영 구성](hosting.md), [운영 성공·거절 증거](../evidence/deployment/https-verification.json)를 참고하세요.
